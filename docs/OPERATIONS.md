### Account policy backend

The account policy registers one computer browser and one phone browser per account. An HttpOnly `tawjihi_device` cookie identifies the browser; `account_devices` permanently stores only its token hash, device class and registration time. Logout revokes the session without releasing a slot. Registration starts with successful sign-ins/account creation or restoration of an existing session after rollout; account identities and progress are preserved. Another browser, private browsing, deleted/expired site cookies, or a replacement device needs administrator recovery when that class's slot is occupied. Recovery must explicitly replace only the verified account's device registration, never its account ID, progress, IndexedDB or pending answers. Browsers cannot read MAC addresses, authenticate physical device classes, or prevent deliberate cookie copying; this is browser registration, not hardware attestation.

Free accounts receive **seven shared browser hearts** per calendar day, resetting at **00:00 Asia/Hebron**, including daylight-saving changes. The first **two visible published lessons in each subject** have unlimited attempts; hidden introductions do not count. Later lessons stay accessible with hearts. `domain/free-practice.js` owns this lesson rule for browser and server, including persisted second-paper mathematics identities. Correct and incorrect attempts in later lessons both cost one heart. The account quota still prevents refreshing hearts by switching devices; the shared browser quota prevents refreshing them by switching accounts. Account progress, gems, purchases and receipts remain separate. Lowering a legacy ten-heart balance clamps hearts without resetting gems or purchased explanations.

`browser_registrations` atomically reserves one signup per browser token; an already registered browser cannot create another account, including after logout/restart. Existing accounts can still sign in subject to their existing device slots. Shared-family-device recovery requires administration; never delete student accounts to release a browser. `browser_heart_attempts` in the existing shared D1 arbitrates free attempts across per-account Durable Objects, using the original account/update ID and request digest. Successful retries never debit twice; definitively rejected updates release their reservation. An interrupted or unknown result retains its reservation for retry rather than permitting overspending. A second browser/cookie reset remains a limitation of browser identification, not proof of a new person.

Free-account answers still require online confirmation before showing their result, including starter lessons. Subscribers can study their purchased subjects and the two free starter lessons in each subject offline; starter explanations are included without gems for every account. Failed/lost acknowledgements retain the original answer and update ID in the durable outbox. Paid answers retain offline saving and their seven-day reconnect requirement. Old trial records and purchased explanations remain intact, but trials cannot grant unlimited access or be activated. Client clocks, posted balances and posted subscription flags do not authorize server-side entitlements.

`QUESTION_JUMPS_REQUIRE_SUPER` in `domain/free-practice.js` makes selecting an unsolved slider question in a later, heart-metered lesson a Super benefit. The first two visible published lessons in every subject allow free students to select any question, even with zero hearts. In later lessons, free students may scroll the slider, select previously correctly solved questions, resume their saved place, follow existing question links and continue sequentially; clicking or keyboard-activating a new slider question opens the paywall without changing the current question. There is no daily skip counter or skip-reset timer. `QUESTION_NAVIGATION_LIMIT_ENABLED=false` keeps historical five-skip allowances/cursors inactive and preserved. Previously solved questions remain freely selectable. Explicit `kind:jump` requests check the current account’s canonical saved solves; a client-supplied solved flag cannot grant access.

Each distinct, first-time correct published question earns **7 gems** for free and paid accounts. Wrong answers, repeated solves, imported history and idempotent retries do not add credits. The additive `answer_gem_rewards` ledger binds each award to its canonical question and original answer update ID; award, balance, progress and acknowledgement commit atomically. Old balances, imports and `learner_gem_rewards` batch-counter units are preserved without retroactive payouts. Versioned balances still reject stale refunds. Answer responses include the original `gemReward` on retries; the browser tracks those receipts per session, so the completion's gem total excludes purchases and other-device earnings. Paid offline answers remain queued and earn server-confirmed gems when synchronized. Ending a written-question session first commits the selected correct/wrong assessment through the same save as Continue; an interrupted confirmation keeps the question and its original retry ID. A wrong answer does not consume the first-correct reward. Session totals include only acknowledged gem receipts. The Super invitation's blue Back button opens the subject roadmap; its heart-only countdown sits beneath the heading under Rocky. Historical navigation tables remain preserved and inactive.

Super is advertised at **₪100 for a full year across all subjects** or **₪15 per year for one subject**. The nine-subject annual bundle is recommended and saves approximately 26% versus nine separate ₪15 subscriptions (₪135 total). Plan selection opens the configured WhatsApp contact with the chosen subjects and price. Payment and account activation remain manual; selecting a plan neither charges nor grants access. Paid accounts retain unlimited questions and explanations plus downloaded offline study, with the existing **weekly reconnect still mandatory** for verification, progress synchronization and release checks. A known subscription expiry or clock rollback can require connection sooner. Existing subscription/account identities and activation behavior are preserved.

### WhatsApp phone verification research (not enabled)

Standard outbound OTP verification uses paid authentication templates; free customer-support messaging is not a promise of free OTP delivery. Meta bills delivered messages by category/recipient market ([pricing](https://whatsappbusiness.com/products/platform-pricing/)). A candidate with no outbound WhatsApp messages is **student-initiated verification**: the website creates an expiring, single-use random challenge, opens WhatsApp with a verification message addressed to Khutwa, receives the student's message through the official Cloud API webhook, and confirms the signup in the website. Meta's [webhook guide](https://whatsappbusiness.com/blog/how-to-use-webhooks-from-whatsapp-business-api/) shows that received messages include the sender number; [Twilio's pricing explanation](https://help.twilio.com/articles/360037672734-How-Much-Does-it-Cost-to-Send-and-Receive-WhatsApp-Messages-with-Twilio-) states that inbound messages carry no Meta fee. A provider such as Twilio can still charge its own inbound fee, so evaluate direct Cloud API integration. Hosting, setup, eligibility and future pricing remain separate; this design is an inference from documented inbound capabilities, not a Meta-provided free OTP product.

Implementation would require a Meta app/business setup, a registered business number and an HTTPS webhook; authenticate webhook signatures, bind each challenge to the pending browser signup and expected normalized phone number, expire/consume it atomically, reject replays and duplicate verified-number registrations, and show confirmation in the website without sending an outbound OTP. A WhatsApp message establishes control of that WhatsApp account, not unique personal identity. Current WhatsApp username support can omit the phone number from incoming webhooks and provide a Business Scoped User ID (BSUID) instead ([Meta announcement](https://developers.meta.com/resources/videos/whatsapp-usernames/), [Twilio webhook changes](https://www.twilio.com/en-us/changelog/whatsapp-usernames--new-business-scoped-user-id--bsuid--field-re)). Never mark a typed phone number verified from a BSUID-only message. Either enforce uniqueness on the verified WhatsApp identity and describe it honestly, or require a verified phone-sharing/OTP fallback. Therefore this is not a confirmed universally free phone-number verification system. Do not automatically attach an existing student's account solely because a recycled phone number matches. No WhatsApp credentials, verification endpoint or messages are configured by this research.

## Approval → push; deploy → publish

1. Review the scoped diff and run relevant local checks. Stage explicit approved paths and commit. **Approved/push** authorizes `git push origin main`; it does not publish.
2. **Deploy/publish** authorizes `npm run deploy`. It requires the correct repo, `main`, and a clean tree, fetches remote main, refuses to overwrite newer work, pushes, explicitly dispatches the full approved commit SHA, and follows that run. `-- --check` performs preflight without pushing or dispatching. Use an isolated checkout when unrelated edits prevent a clean release.
3. GitHub checks out that commit, parses syntax, checks types and deployment behavior, then builds `_site/` once. It verifies the staging account connection before publishing the same build. Final checks verify production's release, lesson catalog, runtime samples, browser libraries, anonymous account API and protected Students route.
4. Report the commit and successful run only after live checks pass. Use `npm run deploy:status` or `gh run view <id> --log-failed`; fix the failed step without restarting unrelated suites.

Pushes never trigger a release, including docs/tests-only pushes. PRs run fast checks. Full Node/content/browser/compatibility suites remain opt-in through `check:full`, `verify:full`, `release:full`. The deployment parses all JS once so earlier approved commits cannot escape syntax checking; it does not download test browsers.

Git pushes changed objects. Pages uploads a complete file manifest and [reuses assets already stored by Cloudflare](https://developers.cloudflare.com/api/resources/pages/subresources/assets/methods/check_missing/). Keep coherent module versioning: a frontend change may rewrite import URLs in several modules so browsers cannot mix releases. Do not replace this with partial directory uploads. Docs, skills, tests, tooling, authoring ledgers and private account data are excluded from the package; required licenses remain.

The old GitHub Pages address already serves the redirect in `docs/index.html` from `main:/docs`. Keep that URL working. Routine Cloudflare deployment does not touch its configuration.

Lesson images are packaged when referenced by the generated content catalog or application source, including hidden/legacy lessons. Unreferenced source crops remain local authoring evidence. Use literal image filenames in authored content; when changing media/loading or packaging, run the focused static-artifact test in `tests/package-app.test.mjs` to check catalog completeness.
